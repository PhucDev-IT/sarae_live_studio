## Concrete CamSwap native concerns

1. `hook_opensles.cpp` assumes Android simple buffer queue vtable `[0]=RegisterCallback`, `[2]=Enqueue`. The [Android `SLAndroidSimpleBufferQueueItf_` declaration](https://android.googlesource.com/platform/frameworks/wilhelm/+/fdef5de17abc6c30b293861ca276259a7dd93837/include/SLES/OpenSLES_Android.h) and local NDK 28.2 header instead specify `[0]=Enqueue`, `[1]=Clear`, `[2]=GetState`, `[3]=RegisterCallback`. On this contract, its typed inline hooks target the wrong functions. The same file stores only `lastBuffer` from `Enqueue`; a multi-buffer FIFO callback need not refer to the last enqueued buffer.
2. `hook_aaudio.cpp` calls the application's original input data callback **before** replacing `audioData`, so data the callback already consumed cannot be replaced afterward. It also interprets the callback return as a frame count, although the standard data callback returns `CONTINUE`/`STOP`. Android documents that input callback `audioData` should not be modified directly and that callbacks must avoid allocations, mutexes and unbounded work. [AAudio NDK reference](https://developer.android.com/ndk/reference/group/audio).
3. [`pcm_bridge.cpp`](https://github.com/HExplorers-Smx/Android-CamSwap-OpenSource/blob/31e8b6d83c3928c7cfc59da7ad2bd5dcfdac7409/app/src/main/cpp/pcm_bridge.cpp) attaches a JVM thread and allocates a Java byte array for PCM replacement; OpenSL wrapper uses a mutex. [`native_audio_hook.cpp`](https://github.com/HExplorers-Smx/Android-CamSwap-OpenSource/blob/31e8b6d83c3928c7cfc59da7ad2bd5dcfdac7409/app/src/main/cpp/native_audio_hook.cpp) returns success unconditionally after installing both hook groups and says release leaves Dobby hooks until process exit. None of this validates the Phase 20 foreign-library lifetime, callback safety, or TikTok LIVE audio path.

## Conclusion and single next direction

No reviewed source proves real Douyin/TikTok LIVE soundtrack delivery or supplies a safe mechanism missing from Sarae Phase 10–20. XVirtualCamera's stream URL changes the **input video source**, not the target's LIVE microphone path. xCam's Java `AudioRecord` approach repeats Sarae Phase 10–11, which passed recording but missed Phase 12 LIVE. CamSwap's native approach is conceptually different but its inspected implementation has concrete ABI/ownership/real-time defects, and its target selection remains unverified. Do not import or deploy it.

**Next direction:** test a class-compliant **USB audio interface as a physical input** to the Samsung, fed from the approved MP4 soundtrack, in one short unpublished TikTok recording before any LIVE consideration. This avoids native-library binding and uses Android's supported external-input route. It remains conditional until actual TikTok routing and saved-file audio are measured; it is not a claim that LIVE audio will work. See [native feasibility decision](NATIVE_AUDIO_FEASIBILITY_DECISION.md).
